name: as-prose
description: Improve the clarity and discoverability of code and its documentation. Clarify names, structure, comments, and public API documentation for engineers encountering the code for the first time.
---

Let names and structure explain the mechanics, public documentation explain the contract, and implementation comments explain reasoning the code cannot express.

## Readability principles

- **Prefer self-explanatory code.** Use the shortest clear name within its scope: an internal `delete_button` does not need its parent component's name. Preserve meaningful distinctions, such as queued refresh versus immediate rebuild. Rename or simplify code when that removes the need for explanation; introduce helpers only when they reduce the reader's work.
- **Comment on non-obvious reasoning.** Capture intent, domain rules, constraints, trade-offs, and hazards. Assume programming experience; omit narration of assignments, pending flags, deduplication, and ordinary control flow. Place each comment beside the code it explains, with enough context to make its causal connection explicit.
- **Reassess existing prose before polishing it.** Derive the explanation the reader needs from the code, its callers, and the task before deciding which old sentences to keep. Existing prose is a draft, not evidence of reader need. Retain, rewrite, relocate, or remove it accordingly; compressing an unnecessary claim still leaves an unnecessary claim. Preserve behavior and meaningful contracts without preserving every sentence written about them. A contract worth documenting changes how a caller uses the API or interprets its results; a verified fact about the implementation is not automatically such a contract.
- **Document stable meaning.** Retain useful units, scope, side effects, and failure behavior; omit incidental delimiters, symbols, visual shades, and internal sequencing. For a negative guarantee or repeated claim, ask what likely misunderstanding its omission would cause and what the reader would do differently. Ground that need in the interface, callers, or task; do not invent hypothetical expectations to justify inherited text. When an existing prerequisite already tells callers what to do, omit a redundant disclaimer about work the function does not perform. Otherwise express the prerequisite as a concrete action, or explain a necessary negative guarantee's practical consequence. Check claims against relevant code paths, including asynchronous completion, defaults, and validation. Investigate uncertain behavior rather than hiding a bug with wording.
- **Introduce modules with connected prose.** Every module in scope needs a top-of-file overview that reads as a short introduction. Establish what the module provides before asking the reader to build, configure, or call it. Develop that idea through its use, broad operation, and essential prerequisites in an order that makes their relationships clear. For an internal module, explain its role and how other code uses it. This is a useful progression, not a required sentence template or a checklist to cover one item at a time. Use complete sentences with clear subjects and antecedents; each sentence should develop the preceding thought. A list of individually accurate facts is not a coherent paragraph. Read the overview as continuous prose, ignoring comment prefixes and line wrapping, and revise abrupt topic changes or unrelated clauses joined by semicolons.
- **Keep introductions and API contracts at their useful levels.** The overview should orient a new reader without requiring a companion guide, while leaving detailed return values, error variants, defaults, and lifecycle rules beside the relevant API. Include a prerequisite or constraint in the introduction when it is essential to starting correctly, and connect it to the operation that requires it. Do not accumulate every exception there to make the overview self-contained. Include a minimal example when it helps; distinguish existing repository configuration from standalone setup. Individual API docs must remain independently useful, with inputs, outputs, defaults, side effects, and meaningful lifecycle/error contracts. An external guide or bare symbol list cannot substitute for the overview.
- **Use native documentation conventions.** Place overviews according to language syntax and required headers. Use tags or wrappers when helpful for clarity or tooling. Use doc comments/docstrings and supported tags for useful contracts and tooling: parameters, returns, errors, examples, generics, deprecation, or links. Do not invent tags, duplicate clear signature types, or annotate every private helper mechanically. Keep API documentation about that API and broader architecture in the module overview.
- **Explain difficult concepts proportionately.** Use a worked example or diagram when it clarifies non-obvious logic. State assumptions and distinguish illustrative values from guarantees. Remove repetition unless needed for independently understandable public documentation; do not turn routine code into a tutorial.

## Review and revision

The coordinator manages scope and verification. Reviewers assess; a separate implementation agent edits. Never use a reviewer as the editor or self-award the final score.

### Prepare

Read applicable repository instructions, target files, relevant docs, and working-tree status. Preserve existing code edits and behavior, including public interfaces, unless changes are authorized. In-scope prose may be removed or rewritten when its meaning is unnecessary or better expressed elsewhere; existing wording is not a preservation requirement. Limit work to the requested component and directly affected docs/tests. Identify appropriate checks; ask for the target only if it cannot be inferred.

### Run the loop

1. **Review independently.** Start a new reviewer with `collaboration.spawn_agent` and `fork_turns: "none"`, or equivalent clean context. Send only target paths, scope constraints, and the reviewer brief below. Do not send this whole workflow, conversation history, prior feedback/scores, suspected problems, proposed fixes, or the target score.
2. **Delegate improvements.** If findings remain, send a different agent the review, target paths, scope constraints, and readability principles. It must verify findings against source, make proportionate improvements, and report changes, checks, and any rejected findings with reasons. The implementation agent may continue across rounds; each reviewer must be fresh.
3. **Verify.** Inspect the actual diff and keep related public docs consistent. For comment-only changes, confirm executable code is unchanged and check syntax/format as appropriate. For refactors, run relevant tests and required checks. Change test expectations only for demonstrably stale expectations or authorized contract changes; never weaken tests to hide regressions. Resolve failures before re-review.
4. **Re-review the revised artifacts.** Repeat from step 1 with the same rubric. Retain unresolved findings in the coordinator's record so a later review cannot silently erase them.

Finish when an independent review gives 10/10 overall and in every dimension, no material findings remain unresolved, and relevant checks pass. If a lower score has no actionable basis, ask that reviewer to clarify its assessment without suggesting a higher score. Do not seek favorable ratings by changing the rubric or repeating reviews without substantive revisions.

Continue while meaningful progress is possible. If delegation or required validation is unavailable, or successive rounds repeat incompatible preferences without progress, report the actual result and unresolved issues rather than claiming success or looping indefinitely. Respect user cancellation, budgets, and existing authorization boundaries; this workflow does not authorize publishing, committing, or unrelated changes.

## Reviewer brief

Supply the actual paths and constraints with this brief:

> Review these files as an engineer encountering the module for the first time. Read applicable repository instructions. Remain read-only and do not consult prior reviews or history.
>
> First read only each top-of-module overview as continuous prose, ignoring comment prefixes and line wrapping. Assess whether it develops a clear introduction, with purpose established before instructions and each sentence building on the preceding thought. Treat disconnected fact lists, unclear antecedents, abrupt topic changes, and unnecessary architectural or implementation detail as actionable findings, even when every fact is accurate. Assess documentation structure for clarity and tooling needs. Then read public API docs for detailed contracts. Finally inspect implementation to verify accuracy and assess whether names or simple refactoring could replace comments. Across overviews, API docs, implementation comments, and guides, assess whether each claim earns its place by helping the reader understand or act. Existing text is not evidence of relevance: flag unnecessary inherited claims for removal or relocation rather than merely requesting shorter wording. For retained negative guarantees and repeated claims, report the likely misunderstanding they prevent and its practical consequence, grounded in the interface, callers, or task. Verifying that they are true, calling them contracts, or inventing hypothetical expectations is insufficient. Preserve meaningful constraints whose absence would mislead callers, and remove disclaimers that merely restate an already clear prerequisite. Companion guides may supplement, but cannot excuse an insufficient module overview.
>
> Score overall and each dimension out of 10:
> 1. **Discoverability:** Module overviews and public API docs are self-contained and useful without overwhelming the reader. A missing or insufficient top-of-module overview is a material finding.
> 2. **Honesty and economy:** No misleading guarantees, needless repetition, incidental decoration, or routine implementation narration.
> 3. **Added value:** Comments convey information code cannot readily express and that the reader needs at that point; names and structure are concise and self-explanatory. Existing claims are reassessed for relevance rather than automatically retained or compressed. Useful contracts survive editing; unnecessary caveats do not survive solely because they are true.
> 4. **Explanatory quality:** Deeper explanations are accurate, locally understandable, and effective. Examples clarify difficult concepts rather than restating mechanics; their absence is not a defect when none are needed.
> 5. **Narrative coherence:** Module overviews read as concise, connected introductions. Sentences have clear subjects and develop a shared idea in a meaningful order; essential constraints follow from that idea. Complete factual coverage does not compensate for fragmented prose or an API reference compressed into the introduction.
>
> Report concrete findings with locations, reader impact, and minimal suggestions. Separate material defects from subjective polish. Rate honestly: 10 means no material improvement is needed under this rubric, not theoretical perfection. Do not inflate scores to satisfy an assumed target.
