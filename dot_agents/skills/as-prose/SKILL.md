description: Improve the clarity and discoverability of code and its documentation. Clarify names, structure, comments, and public API documentation for engineers encountering the code for the first time.
---

Let names and structure explain the mechanics, public documentation explain the contract, and implementation comments explain reasoning the code cannot express.

## Readability principles

- **Prefer self-explanatory code.** Use the shortest clear name within its scope: an internal `delete_button` does not need its parent component's name. Preserve meaningful distinctions, such as queued refresh versus immediate rebuild. Rename or simplify code when that removes the need for explanation; introduce helpers only when they reduce the reader's work.
- **Comment on non-obvious reasoning.** Capture intent, domain rules, constraints, trade-offs, and hazards. Assume programming experience; omit narration of assignments, pending flags, deduplication, and ordinary control flow. Place each comment beside the code it explains, with enough context to make its causal connection explicit.
- **Reassess existing prose before polishing it.** Derive the explanation the reader needs from the code, its callers, and the task before deciding which old sentences to keep. Existing prose is a draft, not evidence of reader need. Retain, rewrite, relocate, or remove it accordingly; compressing an unnecessary claim still leaves an unnecessary claim. Preserve behavior and meaningful contracts without preserving every sentence written about them. A contract worth documenting changes how a caller uses the API or interprets its results; a verified fact about the implementation is not automatically such a contract.
- **Document stable meaning.** Retain useful units, scope, side effects, and failure behavior; omit incidental delimiters, symbols, visual shades, and internal sequencing. For a negative guarantee or repeated claim, ask what likely misunderstanding its omission would cause and what the reader would do differently. Ground that need in the interface, callers, or task; do not invent hypothetical expectations to justify inherited text. When an existing prerequisite already tells callers what to do, omit a redundant disclaimer about work the function does not perform. Otherwise express the prerequisite as a concrete action, or explain a necessary negative guarantee's practical consequence. Check claims against relevant code paths, including asynchronous completion, defaults, and validation. Investigate uncertain behavior rather than hiding a bug with wording.
- **Introduce runtime modules with connected prose.** Each module that implements application or library runtime behavior needs a top-of-module doc comment or docstring. Write the introduction as the module's public contract: explain what callers can use, how they use it, and the observable behavior they can rely on. Name the exported entry points needed to follow that contract, grouping related functions, types, or constants into a coherent explanation. Explain the main input/output shapes and interaction, including caller responsibilities and consequential state, side-effect, failure, or lifecycle rules. Naming an options type or callback is insufficient when the caller still cannot tell what to supply or consume; use actual callable names, essential field names, and data representations to make valid calls concrete in prose, a compact data shape, or a small example. A purpose statement or architectural description alone is insufficient. Clear names and individual API docs complement this introduction; they do not replace it. Scale the introduction to the module: a simple utility may need only one useful sentence, while a screen or stateful service may need a short paragraph connecting its purpose, operation, and essential constraints. Establish purpose before setup or usage instructions, and read the prose continuously to catch disconnected facts, unclear antecedents, and abrupt topic changes. Tests do not need module introductions; descriptive test names and local explanations of unusual setup provide their context. Type-only declarations, re-export-only files, static configuration, and data-only files likewise have no blanket overview requirement. Keep useful contracts or unusual constraints documented locally in those files without adding ceremonial headers.
- **Make the module contract usable on its own.** A reader of the overview alone should be able to identify the public interface, choose the right entry points, and explain the normal interaction and essential obligations without inspecting implementation. Include the contract needed to get started correctly; keep exhaustive parameter details, edge cases, and method-specific rules beside the relevant API. Do not turn the overview into a bare export list, a copy of every signature, or a compressed reference manual. Include a minimal example when it clarifies the interaction; distinguish repository configuration from standalone setup. Individual API docs should still be independently useful for their detailed contracts.
- **Format contracts for readers.** Use the documentation system's inline-code syntax for symbols and short expressions. Put multi-field shapes, signatures, and nontrivial examples in language-labelled fenced blocks or native literal/code blocks, with normal indentation and one field or statement per line; do not squeeze them into wrapped prose. Separate blocks and paragraphs with blank lines, and use lists or short section labels when they clarify distinct workflows. Connected explanation does not mean an uninterrupted paragraph: preserve the visual structure of code and data. Check the source comment and its rendered documentation; prose line breaks may collapse, while code blocks preserve layout. A formatter passing does not establish that a comment is readable.
- **Use native documentation conventions.** Place runtime module overviews according to language syntax and required headers. Use documented language/ecosystem tags or wrappers when they identify the documentation scope or improve navigation and tooling; preserve their actual meaning and supported syntax. Use doc comments/docstrings and supported tags for useful contracts and tooling: parameters, returns, errors, examples, generics, deprecation, or links. Do not invent tags, duplicate clear signature types, or annotate every private helper mechanically. Keep API documentation about that API and broader architecture in the module overview.
- **Explain difficult concepts proportionately.** Use a worked example or diagram when it clarifies non-obvious logic. State assumptions and distinguish illustrative values from guarantees. Remove repetition unless needed for independently understandable public documentation; do not turn routine code into a tutorial.

## Review and revision

The coordinator manages scope and verification. Reviewers assess; a separate implementation agent edits. Never use a reviewer as the editor or self-award the final score.

### Prepare

Read applicable repository instructions, target files, relevant docs, and working-tree status. Preserve existing code edits and behavior, including public interfaces, unless changes are authorized. In-scope prose may be removed or rewritten when its meaning is unnecessary or better expressed elsewhere; existing wording is not a preservation requirement. Limit work to the requested component and directly affected docs/tests. Identify appropriate checks; ask for the target only if it cannot be inferred.

### Run the loop

1. **Review independently.** Start a new reviewer with `collaboration.spawn_agent` and `fork_turns: "none"`, or equivalent clean context. Send only target paths, scope constraints, and the reviewer brief below. Do not send this whole workflow, conversation history, prior feedback/scores, suspected problems, proposed fixes, or the target score.
2. **Delegate improvements.** If findings remain, send a different agent the review, target paths, scope constraints, and readability principles. It must verify findings against source, make proportionate improvements, and report changes, checks, and any rejected findings with reasons. The implementation agent may continue across rounds; each reviewer must be fresh.
3. **Verify.** Inspect the actual diff and keep related public docs consistent. For comment-only changes, confirm executable code is unchanged and check syntax/format as appropriate. For refactors, run relevant tests and required checks. Change test expectations only for demonstrably stale expectations or authorized contract changes; never weaken tests to hide regressions. Resolve failures before re-review.
4. **Re-review the revised artifacts.** Repeat from step 1 with the same rubric. Retain unresolved findings in the coordinator's record so a later review cannot silently erase them.

Finish when an independent review gives 10/10 overall and in every dimension, no material findings remain unresolved, and relevant checks pass. If a lower score has no actionable basis, ask that reviewer to clarify its assessment without suggesting a higher score. Do not seek favorable ratings by changing the rubric or repeating reviews without substantive revisions.

Continue while meaningful progress is possible. If delegation or required validation is unavailable, or successive rounds repeat incompatible preferences without progress, report the actual result and unresolved issues rather than claiming success or looping indefinitely. Respect user cancellation, budgets, and existing authorization boundaries; this workflow does not authorize publishing, committing, or unrelated changes.

## Reviewer brief

Supply the actual paths and constraints with this brief:

> Review these files as an engineer encountering the module for the first time. Read applicable repository instructions. Remain read-only and do not consult prior reviews or history.
>
> First distinguish modules that implement application or library runtime behavior from tests and support files. Every runtime implementation module needs a top-of-module doc comment or docstring, even when its names and individual API docs are clear. A class or function doc comment later in the file does not substitute for the module introduction. Do not require module introductions for tests, type-only declarations, re-export-only files, static configuration, or data-only files. Before reading declarations or implementation, read each runtime overview alone and summarize the public interface and normal interaction it promises: which exported entry points a caller uses, what goes in and comes out, and the essential responsibilities and observable behavior. Mark anything the overview leaves unknown rather than filling gaps from names, prior knowledge, or later API docs. Then inspect the exports, callers, and implementation to verify that the summary is accurate and that no essential part of the public contract was omitted. A header that only describes purpose or internal architecture is insufficient, even when accurate. Likewise, naming public symbols without explaining the essential input, callback, or result protocol leaves the contract incomplete. Check whether a reader can form normal calls using the documented names and representations; gaps that force guessing arguments, fields, or serialized-versus-parsed data are actionable. Assess both the explanation and its visual structure as written and rendered. The prose should form a connected caller-facing explanation, with purpose established before setup or usage instructions and detail proportionate to its behavior. Do not flatten code blocks or lists into prose when reviewing: check paragraph spacing, inline code, language-labelled fences or native literal blocks, and normal indentation. Multi-field contracts or signatures squeezed into wrapping prose are actionable readability defects even when accurate and formatter-clean. Verify any documentation tags against the language/ecosystem conventions; use supported tags when they improve scope or navigation. Improve an unhelpful runtime overview rather than removing the introduction altogether. Flag disconnected facts, unclear antecedents, abrupt topic changes, and unnecessary detail when they impair understanding. Assess documentation structure for clarity and tooling needs. Read public API docs for useful contracts, then inspect implementation to verify accuracy and assess whether names or simple refactoring could replace implementation comments. Across overviews, API docs, implementation comments, and guides, assess whether each claim earns its place by helping the reader understand or act. Existing text is not evidence of relevance: flag unnecessary inherited claims for removal or relocation rather than merely requesting shorter wording. For retained negative guarantees and repeated claims, report the likely misunderstanding they prevent and its practical consequence, grounded in the interface, callers, or task. Verifying that they are true, calling them contracts, or inventing hypothetical expectations is insufficient. Preserve meaningful constraints whose absence would mislead callers, and remove disclaimers that merely restate an already clear prerequisite. Companion guides and individual API docs may supplement, but cannot replace, a runtime module overview.
>
> Score overall and each dimension out of 10:
> 1. **Discoverability:** Runtime overviews expose a usable public contract: callers can identify the relevant exports, follow the normal interaction, and understand essential inputs, results, and obligations from the overview alone. A missing runtime overview or one limited to purpose/architecture is a material finding; later API docs cannot make up for it. Tests and support files are not penalized for lacking headers.
> 2. **Honesty and economy:** No misleading guarantees, needless repetition, incidental decoration, or routine implementation narration.
> 3. **Added value:** Comments convey information code cannot readily express and that the reader needs at that point; names and structure are concise and self-explanatory. Existing claims are reassessed for relevance rather than automatically retained or compressed. Useful contracts survive editing; unnecessary caveats do not survive solely because they are true.
> 4. **Explanatory quality:** Deeper explanations are accurate, locally understandable, and effective. Examples clarify difficult concepts rather than restating mechanics; their absence is not a defect when none are needed.
> 5. **Narrative coherence and presentation:** Prose develops a shared idea in a meaningful order, with clear subjects and connected constraints. Code and structured contracts retain readable layout through native inline-code and block syntax, indentation, spacing, and useful lists or section labels. Complete factual coverage does not compensate for dense paragraphs or multi-field shapes flattened into prose. Assess source and rendered output rather than relying on formatter success. Do not penalize tests or support files for having no overview.
>
> Report concrete findings with locations, reader impact, and minimal suggestions. Separate material defects from subjective polish. Rate honestly: 10 means no material improvement is needed under this rubric, not theoretical perfection. Do not inflate scores to satisfy an assumed target.
